# Retrospective

> Flexible skill. Run effective retrospectives: gather data, identify patterns, generate actionable insights, and track follow-through. Turn past experiences into future improvements.

## Overview

A retrospective is a structured meeting at the end of a work cycle (sprint, project, release) where the team reflects on what happened and identifies ways to improve. The goal is not to assign blame but to understand the system's behavior and make targeted changes.

**Core Principle**: The team that does not reflect is doomed to repeat its mistakes. Retrospectives are investments in the team's future velocity and quality.

## Step-by-Step Process

### Phase 1: Set the Stage
1. Define the time period or scope of the retro (last sprint, last release, last incident).
2. Set a safe, blame-free tone. Retrospectives are about the system, not the individuals.
3. Remind the team of the goal: identify actionable improvements for the next cycle.

### Phase 2: Gather Data
1. **What went well**: Wins, successes, things to celebrate.
2. **What didn't go well**: Pain points, frustrations, failures, delays.
3. **What was confusing**: Mysteries, unclear processes, unanswered questions.
4. **What to continue**: Practices that should be maintained or strengthened.

### Phase 3: Generate Insights
1. Group related items into themes (process, communication, tools, skills).
2. Look for patterns: the same issue appearing in multiple cycles is a systemic problem.
3. Ask "why" 3-5 times for each major issue to find the root cause.
4. Identify the most impactful 1-3 areas for improvement.

### Phase 4: Decide Actions
1. For each improvement area, define a specific, measurable action.
2. Assign an owner for each action item.
3. Set a deadline or check-in date.
4. Limit action items to 3. More items means nothing gets done.

### Phase 5: Close
1. Summarize the key insights and action items.
2. Thank the team for their participation and candor.
3. Document the retro output in a shared location.

## Common Mistakes

- **No follow-through**: Action items from the previous retro are not reviewed or not completed.
- **Blaming individuals**: Retrospectives are about the system. If the same person makes the same mistake, the process is broken.
- **Too many action items**: 5+ action items dilute focus. Pick the top 3.
- **No safe environment**: If team members are afraid to raise issues, the retro is useless.
- **Skipping retros when the team is "too busy"**: The busiest teams need retros the most.

## Quality Gates

- [ ] Retro data is collected from multiple sources.
- [ ] Root cause analysis is applied to major issues.
- [ ] Action items are specific, measurable, and assigned to owners.
- [ ] Previous retro action items are reviewed for completion.
- [ ] Retro output is documented and accessible to the team.
